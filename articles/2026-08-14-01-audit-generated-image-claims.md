技術資料に緑色のチェックマークと「CI SUCCESS」、その横に「37%改善」と書かれている。実行履歴と測定結果を見て作った図なら、有用な要約である。生成AIが同じ見た目を描いただけなら、その図から成功や改善を判断することはできない。

**図には事実を説明させる。事実そのものを作らせない。** これは画像の美しさではなく、説明と証拠の役割を分ける設計である。

## 見た目の完成度と事実の確かさは別である

次の文字列は説明用の架空例であり、実測結果ではない。

| 図の文言 | 事実として載せるために必要なもの |
| --- | --- |
| CI SUCCESS | 対象コミットに対応する実行結果 |
| P99: 42 ms | 計測条件と元データ |
| 37%改善 | 比較前後の値、共通の測定定義、計算式 |
| PR #123 merged | 対象PRの実際の状態 |

画像が正しく表示されることは、これらの情報が正しいことを意味しない。生成されたGitHub風の画面を、GitHubの実行履歴の代わりに扱ってはいけない。

記事制作基盤では、画像の目的を読者理解とし、固定枚数ではなく説明上の価値を要求する方針を採っている。[当時の設定](https://github.com/KAFKA2306/articles/blob/1c41d61b2edd96da33038d9525b952efe5d06aec/pipeline/config.json)・[当時の実装](https://github.com/KAFKA2306/articles/blob/1c41d61b2edd96da33038d9525b952efe5d06aec/pipeline/audit.py)。この方針は編集上の設計判断であり、画像を使った場合の読者理解の改善率を測った結果ではない。

## 数字は生成せず、計算から持ってくる

例えば改善前18.7%、改善後0.6%という架空の数値を考える。差は18.1ポイント、相対的な減少率は約96.8%である。画像生成時に「95%改善」と付け足せば、もっともらしくても計算と一致しない。

本物の測定値なら、測定データから表やグラフを生成する。生成AIには配置や説明構造を作らせ、数値を描画する必要がある場合は確定した値を使う。最新の価格や実行状態のように変化する情報は、静止画に焼き込むより本文や更新可能な画面に置く方が扱いやすい。

## 手元の図を一枚、作り直す

数字や状態を含む図を一枚選び、次の三種類に分ける。

| 図の要素 | 置き場所 |
| --- | --- |
| 関係・構造の説明 | 図に残す |
| 数値・実行結果・外部状態 | 元資料に結びつけ、確定値から表示する |
| 根拠のない数値や因果 | 削除するか、説明用の仮定と明示する |

例えば処理の流れを示す図なら、実測していない処理時間は削っても構造を説明できる。性能比較が目的なら、処理時間を削るのではなく、測定結果からグラフを作る。

実際に取得したスクリーンショットや観測画像は、取得条件を明示すれば証拠になり得る。生成された画面のイラストとは来歴が異なる。図を増やす前に、本文では理解しにくい関係が何かを決める。その関係だけを説明できれば、余計な事実を画像へ持ち込む必要はない。
