**AIに引き継ぐのは会話ではなく、対象・合格条件・観測結果・再開位置だ。** 別のAIが同じ仕事を安全に再開できるかは、説明文の長さではなく、何を変更し、何を見て合格とするかを取り違えないことで決まる。

たとえば、Unityの衣装を別のアバターへ移す仕事を任せたAIが「変換できました」と報告する。次の担当がその結果を引き継いだとき、変換の実行と見た目の成功を区別できなければ、失敗した衣装を完成品として扱ってしまう。

## 実例：処理が終わっても衣装は完成しなかった

2026年10月9日、[Unityアバター改変の記録（固定版）](https://github.com/KAFKA2306/avatars2509/blob/26328d0fe792ac6b83e157fb8a9a268ff8535b4f/Docs/MOCHIFITTER.md)では、Milltina向け衣装をRuruneへ `RetargetOutfit` で変換した。

| 観測した項目 | 結果 |
| --- | --- |
| 適合度 | 21.4% |
| 不一致の骨 | 173本 |
| 骨の対応 | 右脚が左脚に対応 |
| 見た目 | 手首に黒い板が突き出し、失敗 |

同じ記録には、変換前に互換性と左右の対応を確認する条件、変換後に正面・左右・背面を目視確認する手順がある。貫通が0でも目視確認を省略しない。数値の閾値はこのプロジェクトの条件であり、他のアバターや別製品の一般的な合格基準ではない。

この失敗から導くべきことは「別のAIへ衣装変換の長い説明を渡す」ではない。次の担当がどの実物に対してどの条件を確認し、未完了ならどこで止めるかを再現できるようにすることだ。

## 引き継ぐ情報を四つに分ける

| 残すもの | 最小の保存先 | 役割 |
| --- | --- | --- |
| 対象と依頼 | Issue、対象の識別子、入力の版 | 誤った対象に変更を加えない |
| 手順と根拠 | 既存のAGENTS.md、Skill、一次記録 | 必要な知識だけを参照する |
| 合格条件 | Issueまたは既存テスト | 実行前に何を確かめるか固定する |
| 結果と再開位置 | コミット、実行ログ、Issue | 完了と未完了を区別する |

実行能力と権限は保存した説明とは別に、再開する時点で確かめる。たとえばMCPは現在のツール一覧と入力スキーマを提供するが、共有ファイルに操作名を書くだけではツールは接続されない。[MCP Tools仕様](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

次の担当が同じ対象を開けない、必要な権限がない、証拠を読めない場合は、成功として処理せず、その条件を満たすまで止める。

## 一件の作業から始める

既存のIssueを一件選ぶ。以下は上記の失敗を引き継ぐために作った**記入例**であり、新たなUnity実行の記録ではない。

| 項目 | 記入例 |
| --- | --- |
| 対象 | Milltina向け衣装をRuruneへ変換する作業。実行前に実物のPrefabパスとGUIDを確認 |
| 根拠 | 上記2026年10月9日の固定版記録 |
| 合格条件 | 骨の左右対応、必須参照の解決、4方向からの見た目 |
| 最後の確認 | 過去の変換は21.4%、173本不一致、外観失敗 |
| 状態 | 未完了。次の実行前に現行のアセット、対応条件、ツールを確認 |

次のAIには、このIssueと対象プロジェクトの規則、証拠のURLを渡す。最初に現在の対象と版を読み直し、既存の合格条件で不足している観測だけを実行する。過去の失敗をそのまま現在の状態とみなさない。

同じ構造はWebの公開、データ移行、3D制作にも適用できる。たとえばWebなら「コミットをpushした」ではなく「公開先で指定の操作ができる」、データ移行なら「処理が終了した」ではなく「対象集合と件数、失敗行を照合できる」を合格条件とする。これらは応用例であり、この記事での追加実測ではない。

## ファイルを増やすのは、今の仕組みでは足りないときだけ

まずGit・Issue・既存テストで再開できるか試す。手順が複数案件で本当に繰り返されるなら、[AGENTS.md](https://agents.md/)や[Agent Skills](https://agentskills.io/specification)へ移す。ホストごとの指示ファイルには同じ長文をコピーせず、必要な正本への入口を置く。

依頼と結果を複数の実行環境で自動処理する必要が生じて初めて、[JSON Schema](https://json-schema.org/draft/2020-12/)による検証や、[Git submodule](https://git-scm.com/book/en/v2/Git-Tools-Submodules)等の固定版配布を検討する。

たとえば、依頼の合格条件IDが `reference-audit` と `visual-review` の2つなら、結果には同じ2つが一意に存在することを確かめる。後者を削った結果を合格させない。全項目にPASSと書いてあっても、実物を確認するための証拠がなければ完了ではない。JSONの構造検証とUnity実機の検証は別の仕事だ。

以前検討した独自の共有パッケージ、スキーマ、検証スクリプトの設計例は[当時の原稿（固定版）](https://github.com/KAFKA2306/articles/blob/5f01a8b42eb40c3db80c573e289c371ce6b11ecc/articles/2026-11-09-portable-agent-contracts.md)に残している。この設計は標準仕様でも、複数AI間での動作実績でもない。新しい独自形式を必要としない作業では導入しない。

## 反例と導入をやめる条件

一回で完了し、同じ担当が実物と合格条件を直接確認できる作業なら、引き継ぎ専用のファイルを追加する理由はない。また、対象の権限や合格条件が根本的に違う二つの仕事を、同じ契約で実行させると誤操作につながる。

導入効果は同じ作業を、通常のIssueと既存手順だけで渡した場合、構造化した依頼・結果を追加して渡した場合で比較する。確認項目の漏れ、追加説明の回数、再開時間、維持費を測る。追加形式がこれらを改善しなければ廃止する。この比較は未実施であり、優位性は主張しない。

**次のAIに前のAIの完了報告を信じさせる必要はない。** 同じ対象・合格条件・証拠を開ける状態を残し、その場で確認できる範囲だけを成果として引き継ぐ。
