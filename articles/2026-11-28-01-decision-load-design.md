AIに仕事を任せるために、指示書を書く。指示書が増えたので、どれに従うかを決める規約を書く。その規約を維持する担当を作る。

実行能力は増えている。しかし、実行する前に判断しなければならないことも増えている。

この問題に対して、判断を高速化するだけでは不十分だ。**新しい能力を獲得するとき、それを運用するための判断負荷まで増やさないことを設計条件にする。**

本稿では、Kafstylerという複数のAIエージェント向け共通基盤の変更履歴を材料に、目標・測定・改善手順を一つの方法として定義する。実測で確かめられた組織全体の効果と、ここで提案する方法は区別する。

## 成長しても、管理負荷は増やさない

案件数が10倍になり、管理時間が2倍になったとする。案件当たりの管理時間は5分の1なので、効率化には成功している。しかし、管理を引き受ける人の仕事は2倍になっている。

同じ品質の成果を10倍に増やしながら管理時間を半分にできた場合とは、区別するべきだ。

| 状態 | 同等品質の成果数 | 月間管理時間 | 成果当たりの管理時間 |
| --- | ---: | ---: | ---: |
| 変更前 | 10 | 100時間 | 10時間 |
| 効率化 | 100 | 200時間 | 2時間 |
| 負荷一定 | 100 | 100時間 | 1時間 |
| 負荷の反転 | 100 | 50時間 | 0.5時間 |

これは説明用の仮定であり、実測値ではない。

組織の能力や成果を増やすことと、管理負荷を増やすことを切り離す。さらに成果を増やしながら総管理負荷を減らす状態を、本稿では「組織エントロピーの反転」と呼ぶ。熱力学的なエントロピーを測るという意味ではない。

成果の種類や難易度が違えば単純な件数比較はできない。比較する仕事、品質、安全性、利用者への提供条件を先にそろえる。人間の管理時間が減っても、AIの運用費用や別部署の負担が増えたなら、その増分も評価する。

## 将来必要になる判断を負債として扱う

新しい機能を追加するとき、その機能の実装費用は見積もりやすい。一方、使い方を選ぶ、仕様を探す、例外を判断する、更新する、廃止するという費用は、追加した後に発生する。

この将来の反復判断を「判断箇所負債」と呼ぶ。

判断箇所とは、特定の状況で、担当者が複数の可能性から実行する行動を選ぶ必要がある場所である。同じ規約が100ファイルに存在していても、必ず100個の独立した判断があるとは限らない。各ファイルで別々に採否や例外を決める必要があるかを見る。

| 判断箇所 | 判断が発生する条件 | 構造的な削減候補 |
| --- | --- | --- |
| 最新仕様を探す | 作業を始める | 更新元を一つにし、入口から参照する |
| 実行方法を選ぶ | 定型処理を実行する | 共通のコマンドに統一する |
| 更新の要否を決める | 定期起動する | 機械的に差分を判定する |
| 新旧の方式を選ぶ | 移行後も旧方式が残る | 後継へ切り替えて旧経路を廃止する |
| 担当を決める | 複数担当が同じ対象を扱う | 役割と書き込み権限を明確にする |

判断の数だけでは費用は分からない。年に一度の判断と、毎日必要な判断では削減効果が違う。判断の所要時間、誤判断の影響も異なる。

一定期間の判断費用を、次のモデルで見積もる。

$$
D = \sum_{i=1}^{n} f_i(c_i + p_i l_i)
$$

- $f_i$：期間内の判断発生回数
- $c_i$：一回当たりの判断費用。探索・解釈・調整を含む
- $p_i$：誤判断の確率
- $l_i$：誤判断した場合の損失

費用を合計する際は金額などの共通単位に換算する。時間と金額をそのまま足さない。誤判断による連鎖的な損失を重複計上しない。確率や損失が不明なら、実測値・推定範囲・未確認を区別し、精密な数字を捏造しない。

これは提案する費用モデルであり、妥当性が確立された標準指標ではない。実務では、まず人間の判断時間、介入回数、AI利用費用、障害対応費用を別々に記録するだけでもよい。

例えば10個の定型作業で、それぞれ月12回、実行方法の選択に5分かかるなら、月10時間となる。共通の入口によってその選択を不要にできれば削減候補になる。ただし、共通入口の保守時間と障害対応が月10時間以上なら採用する理由はない。この数値も説明用の仮定である。

## 判断を減らすには、読む量や機能数を減らすだけでは足りない

Kafstylerの実行契約は、以前は一つの `COMMANDS.md` に多数の領域の操作方法をまとめていた。コミット [bc5d2cc](https://github.com/KAFKA2306/kafstyler/blob/bc5d2cc801a364bf580d86de441d7754903762e3/COMMANDS.md) と、その次の [25afa78](https://github.com/KAFKA2306/kafstyler/commit/25afa7800567fdd5321502ccf730d12816c27212) を比較すると、次の変更がある。

| 項目 | 変更前 | 変更後 |
| --- | --- | --- |
| COMMANDS.md の行数 | 209行 | 36行 |
| 詳細な実行契約 | 一つの文書内 | 知識・エージェント・開発・制作の4領域に分離 |
| 既知の共通タスク | 採用済み定義を利用 | 共通コマンドを直接実行 |
| 未知のタスク | 実行契約内から探す | 索引から必要な契約へ移動 |

行数はGitHubから取得したUTF-8本文の末尾空白を除き、改行で分割して数えた。36行は索引の行数であって、分離後の文書総量ではない。読解時間やトークン費用の削減率を示すものでもない。

変更後は、既知の操作なら `mise run TASK ARGS` を使い、未知なら `mise tasks` から探す構造になっている。

さらに、モデル選定器の実体は後の[コミット c8850fb](https://github.com/KAFKA2306/kafstyler/commit/c8850fbd5f1d71f3d0ce108b856dc70f0fc8ba51)で移動した。

```text
変更前: node .agents/select-models.mjs
変更後: node skills/adjudicate/scripts/select-models.mjs
共通入口: mise run model-select
```

実装の配置が変わっても、利用者が覚えるタスク名は変わらない。配置場所の変更を利用者の新たな選択にしない設計である。変更前後の `mise.toml` とコミット差分から確認できる。実際のモデル選定結果や実行時間の同等性を今回測定したわけではない。

ここで重要なのは、文書を減らすことと判断を減らすことが同義ではない点だ。

同じ25afa78では、不要な仕組みを廃止するSkillも6行まで圧縮された。しかし後続の[コミット60918ff](https://github.com/KAFKA2306/kafstyler/commit/60918ff6d60aa5d2ecdc7e8c982c28ae6587f561)では23行へ戻し、廃止候補の分類、依存関係、後継の能力、保持すべき情報、認可などの判断基準が明記された。

行数の削減を成功指標にしていれば、この変更は後退になる。しかし判断基準を削ると、次の担当者が毎回それを補う必要が生じる。必要な判断を支える情報は残すべきである。この履歴は、短さではなく判断負荷を評価すべき理由を示す構造上の事例であり、復元後の時間短縮を実証するものではない。

## 自分自身を縮小できる改善機構を持つ

判断を減らすために新たな管理制度を作り続けると、その制度の維持が次の仕事になる。

そこで、改善を担当する仕組み自身も削減対象にする。Kafstylerでは、[MISSION](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/MISSION.md)に減算優先を置き、[decommission Skill](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/skills/decommission/SKILL.md)で廃止の手順を定めている。

本稿でいう「自己減算型知能機関」とは、自らの機能を増やすだけでなく、自らの規約、担当、ジョブ、ツール、実行経路を廃止する権限と手順を持つ組織である。AIである必要はない。

改善候補は次の順に検討する。

| 方法 | 適用条件 |
| --- | --- |
| 削除 | 必要な成果に寄与せず、保持情報や依存先がない |
| 統合 | 同じ判断や成果を複数箇所で扱っている |
| 置換 | 既存の標準機能で必要な能力を担える |
| 確定処理化 | 明確な入力と規則から結果が決まる |
| 現状維持 | 変更による利益が費用やリスクに見合わない |
| 追加 | 他の方法では必要な能力を満たせない |

これは探索の順序であり、無条件に削除案を採用する順位ではない。必要な成果・安全・権限・データ保持を満たす案の中で、総費用と判断負荷を比較する。

定期処理なら、差分を機械的に取得し、正常な無変更の場合にはAIを起動しない。取得失敗は無変更に置き換えない。意味の判断が必要な場合だけAIに渡す。後継が機能を引き継いだら、認可範囲で不要な旧経路を停止する。改善担当の定期ジョブ自身も、起動し続ける価値がなければ統合または廃止する。

## 第三者が実践できる手順

次の手順を、既存の改善作業に組み込む。新しい管理台帳や会議を常設する必要はない。

1. 維持すべき成果を定義する。対象業務、提供件数、品質、安全、必要な権限を固定する。
2. 既存の作業履歴から、反復する判断を特定する。発生条件、担当、選択肢、根拠、頻度、時間、誤判断の影響を把握する。
3. 削除・統合・置換・確定処理化・維持・追加を比較する。失われる能力と新たに発生する判断を含める。
4. 必要な情報と利用経路を後継に移し、認可された範囲で不要な旧方式を廃止する。
5. 同じ仕事量・構成・品質条件で、変更前後の判断時間、介入回数、費用、エラーや手戻りを比較する。仕事量が増えた場合は総負荷と成果当たり負荷を両方見る。
6. 移行費用を含めても利益が残るか判断し、効果がなければ戻すか修正する。改善活動自身の維持負担も同じ基準で扱う。

例えば、請求処理の部署で担当者ごとに異なる金額確認規則を使っている場合、規則を共有するだけで各担当者の判断が不要になるかを調べる。法令・契約ごとに例外が異なるなら一律化しない。明確に決まる確認だけを処理へ組み込み、例外時の責任ある判断は残す。

これは他分野への適用仮説であり、この部署で実測した事例ではない。

## 既存の方法論との違いと、反証条件

Galbraithの組織設計論（1974年）は、情報処理能力を高めるだけでなく、組織が処理する必要のある情報を減らす設計を提示している。

https://jaygalbraith.com/organization-design-an-information-processing-view/

AdamsらのNature論文（2021年）は、問題解決で有益な減算案を見落としやすいことを実験で示している。

https://www.nature.com/articles/s41586-021-03380-y

したがって、判断の必要性を減らすことも、追加より削除を考えることも、本稿が初めて提唱するわけではない。

本稿の提案は、次の三つを一つの設計契約にまとめることにある。成果の増加と総管理負荷の減少を目標にする。将来発生する反復判断を費用として扱う。改善機構そのものにも削除・統合・廃止を適用する。

この方法は次の場合に成立しない。

- 判断箇所を減らした結果、残った判断に必要な時間や損失が増える。
- 総管理時間の減少が、成果や品質の低下によるものである。
- 利用者や別部署に負担が移っただけである。
- 短期的に減らした判断の代わりに、長期の障害対応や保守が増える。
- 必須の承認、責任分担、データ保全、安全上の判断まで省略してしまう。

Kafstylerの公開変更履歴から確認できたのは、入口の統一、詳細の分離、削減後の判断基準の再整備という構造の変更である。組織全体の総管理負荷が実際に減少したかは、同等条件の運用記録が必要であり、未確認である。

## 結論

次に新しい規約、ツール、AIエージェントを追加しようとするとき、実現できる能力とともに、将来必要になる判断を列挙する。そして、その判断を発生させない構造を先に比較する。

**能力を増やすたびに、管理する仕事まで増やさない。**

成果が増えたかだけでなく、何を判断しなくてよくなったかを、組織の成長として評価する。
