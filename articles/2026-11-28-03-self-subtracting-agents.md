**改善を担うエージェント自身も廃止の対象にする。** ただし、削除するのは不要になった仕組みであり、利用者が必要とする能力や情報ではない。

この開発方針を「自己減算型知能機関」と呼ぶ。Kafstylerの廃止・統合原則を整理した名称であり、自己廃止の効果が査読で確立されたという意味ではない。

## 1. 問題：改善案の探索が追加に偏る

Adamsら (2021) は8実験で、人が有益な削除案を見落としやすいことを示した。第4実験の改善条件では、削除案を一つ以上挙げた割合は、削除を考えるよう促さない群で21%、促した群で48%だった [1]。

削除案を比較対象に入れる根拠であって、削除自体が常に改善になることを示したものではない。

## 2. 中心命題：改善の仕組み自身にも廃止を適用する

[KafstylerのMISSION](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/MISSION.md)は追加より減算を先に考え、後継へ切り替えた後に旧経路を廃止することを原則とする。

必要な能力を保持したまま不要な構造を減らす。改善ジョブ自身が役割を終えた場合も例外にしない。削除件数や文字数を成果にしない。

## 3. 定義：削除・統合・置換・維持・追加を区別する

| 選択肢 | 採否を決める条件 |
| --- | --- |
| 削除 | 必要な成果への寄与も、保持すべき固有情報もない |
| 統合 | 重複する役割を一つの後継で担える |
| 置換 | 外部標準ツール等で必要な能力を引き継げる |
| 維持 | 変更の利益が費用やリスクに見合わない |
| 追加 | 既存構成では必要な能力を満たせない |

これは著者の採用方針であり、統計的に最適と実証された順位ではない。認可、安全、データ保全はどの案でも保持する。

## 4. 仕組み：複雑な構成を採用する前に既存構成と比べる

Kimら (2026) は3系統のLLM、6種類のベンチマークの260構成について、同じ計算予算などで単一・複数エージェントを比較した。単一構成の基礎性能が協調の利点を説明する重要な要因だった [2]。

Narayanan & Feigh (2026) はエージェント間の依存がある条件で監督負荷が増えたと報告している [3]。

KISS、YAGNI、疎結合は既存の開発原則である。本稿の方針は、追加を避けるだけでなく、既に存在する仕組みも比較対象に戻すことである。

## 5. 測定：廃止件数ではなく、残る負担と能力を観測する

| 評価項目 | 変更前後で比較する対象 |
| --- | --- |
| 必要な能力 | 同じ受入条件を満たす業務と利用経路 |
| 判断負荷 | 第2部の判断頻度・人間の時間・失敗 |
| 運用費用 | AI起動、外部サービス、維持費 |
| 移行費用 | 切替、情報移行、必要な復旧対応 |
| 保持条件 | 利用者データ、出典、識別子、認可、安全 |

移行費用は継続的な維持費用と区別する。対象期間内で費用を比較する。記録がなければ効果を未測定とする。

## 6. 実践：後継へ切り替えてから旧経路を廃止する

Kafstylerの[decommission Skill](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/skills/decommission/SKILL.md)を参照する。

1. 対象の目的、利用経路、依存、読み書きの担当、保持情報を特定する。
2. 削除・統合・標準ツールへの置換・維持・追加を比較する。必要な能力を失う案は採用しない。
3. 後継と正本を決め、旧方式固有の情報、ID、出典、利用者データを引き継ぐ。
4. 認可された範囲で後継へ切り替え、不要な旧経路、設定、ジョブ、参照を廃止する。判断不能な対象は保持する。
5. 廃止した対象、後継、残る負担を記録し、第1部と第2部の観測へ戻す。

この手順は既存の開発方針を説明したものであり、比較試験で効果が確立された標準手順ではない。

### 採否を決める順序

まず必要な能力、利用経路、保持情報、認可を満たさない案を除く。残った案で、削減できる判断・運用費用と、移行で増える負担を比較する。優劣を判断できなければ保持する。削減のために新たな常設ジョブや承認制度を設けることも、追加案として扱う。

## 7. 根拠：廃止の種類によって必要な調整は異なる

Matsuo (2026) は日本企業の知的財産部門の管理者385人の自由記述から、既存の手順や知識を手放す取り組みを効率改善、ネットワークの再構成、戦略の変更に分類した。上層部や他部門との連絡との関連は取り組みの種類で異なった [4]。

観察研究であり、連絡を減らす介入で効率が上がると証明したものではない。自律エージェントの自己廃止の実験でもない。

Kafstylerでは、定期起動・差分取得は既存OS・CLIに委譲し、正常な無変更と失敗を区別する。規約、ジョブ、旧方式も廃止対象にする。[作業規約](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/AGENTS.md)の記述は参照実装の設計事実であり、削減効果の実測値ではない。

### 反例：廃止手順そのものを短くしすぎた

Kafstylerのdecommission Skillは[圧縮版](https://github.com/KAFKA2306/kafstyler/blob/25afa7800567fdd5321502ccf730d12816c27212/skills/decommission/SKILL.md)で6行となった。その後の[改訂版](https://github.com/KAFKA2306/kafstyler/blob/60918ff6d60aa5d2ecdc7e8c982c28ae6587f561/skills/decommission/SKILL.md)は23行で、廃止候補の分類、依存、後継の能力、保持情報、認可、判断不能時の扱いを具体的に記した。行数は取得本文の末尾空白を除いた改行数に基づく。

この変更では、短さよりも必要な判断基準を保持する方針が明確になった。第2部の棚卸しに当てはめると、廃止対象を選ぶ条件そのものが保持対象となる。行数の増加だけで悪化と判定しない。改訂による判断時間の変化や失敗率は未測定なので、改善効果は断定できない。

## 8. 反証条件：能力を失ってまで小さくしない

必要な能力や利用経路が失われた、障害時の復旧が困難になった、他者へ負担を移した、移行と新方式の維持費が削減効果を上回った場合は改善とみなさない。

不可欠な入力、依存、認可、安全、データ保全の制御は残す。削除件数だけでは採否を判定しない。

## 9. 標準仕様案：変更後の観測を次の改善へ返す

入力は第2部で特定した判断箇所、現在の利用経路、依存、保持条件、権限。出力は採用した変更、廃止・保持した対象、後継、移行費用、変更後の判断負荷と成果、未測定項目。

観測結果を第1部の成功条件へ返し、次の対象選定に用いる。無変更が適切な場合は何もしない。自律エージェントが自身の改善機構を廃止する長期効果は今後の実証課題である。

## 連載の位置づけ

第2部の削減候補と保持条件から変更を選ぶ。変更結果は第1部の成果・能力・管理負荷と、第2部の判断箇所に返す。
