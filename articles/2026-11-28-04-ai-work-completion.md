**AIに生成を急がせる前に、利用者が何をできれば仕事が終わるのかを決めよ。生成量ではなく、成果が届くまでの人間の負担を減らせ。**

## はじめに：ロケットスタートの対象を変える

中島聡氏の『なぜ、あなたの仕事は終わらないのか』は、期限までの最初の2割で仕事の8割を仕上げるロケットスタート時間術を提唱した。2016年の単行本から10年、[2026年の文庫版](https://www.hanmoto.com/bd/isbn/9784868450863)が刊行された。同年11月12日の[PRESIDENT Onlineのインタビュー](https://president.jp/articles/-/121908?page=1)では、中島氏自身がコードの生成をAIへ任せるようになったと語っている。

早い試作によって不確実性を発見し、手戻りに備えるという原理は今でも有効だ。変わったのは、試作する主体と、仕事の完了を妨げる要因である。AIに初稿を書かせる時間が短くても、その後の判断、調整、修正、統合、配布が残っていれば仕事は終わらない。

本稿は原著の6章の問題意識に対応する独立した考察である。AI時代のロケットスタートを、完了条件、裁量、小バッチ、知能基盤の設計として捉え直す。

## 第1章 なぜ、AIを使っているのに仕事は終わらないのか

### 速くなった感覚と実際の完了時間

[METRの2025年7月のランダム化比較試験](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)では、経験豊富なOSS開発者16人が、自身のよく知るリポジトリの実課題246件（平均約2時間）に取り組んだ。AI利用の可否を無作為に割り当てた結果、AI利用可の課題は利用不可より19%長くかかった。開発者は事前には24%の短縮を予想し、実験後も20%速くなったと感じていた。

これは2025年初頭のツールと特定の熟練者についての結果であり、現在の全モデルや全業務が遅くなることを意味しない。[2026年2月のMETRの更新](https://metr.org/blog/2026-02-24-uplift-update/)も、AI利用の普及による選択バイアスなどを踏まえ実験設計を変更している。重要なのは、速度の主観評価が完了時間と逆方向になり得ることだ。

[DORAの2026年3月の分析](https://dora.dev/insights/balancing-ai-tensions/)では、2025年調査で技術職の90%が仕事でAIを使い、80%超が生産性の向上を感じていた一方、AI利用の拡大はデリバリーの処理量と不安定性の両方の増加に関連した。生成が速いことと、安定して届けられることは別である。

### 遅延が移動する三つの場所

- 試作から本番への統合。DORAは、初期生成の節約時間が監査・確認へ移り、試作品と本番品質の間に隔たりが生じると指摘する。
- 受け手への負担の転嫁。[BetterUp LabsとStanford Social Media Labの2025年9月調査](https://www.betterup.com/workslop)（米国のフルタイムのデスクワーカー1,150人）では、40%が直近1か月に内容の乏しいAI生成物（workslop）を受け取り、対処に1件平均約2時間を要した。送り手が節約した時間を受け手が支払う。
- 判断の割り込み。[Microsoftの2025年6月の報告](https://www.microsoft.com/en-us/worklab/work-trend-index/breaking-down-infinite-workday)では、通知受信量上位20%のユーザーにおいて、8時間の主要勤務時間内の通知間隔は平均約2分、24時間の通知数は1日275件だった。全従業員の平均ではないが、通知が多い環境の集中時間の制約を示す。

たとえば、AIが報告書を10分で作り、同僚が誤りの確認と修正に60分費やしたとする。従来60分で完成していた同じ報告書なら、組織としては10分の負担増だ。これは仮定例であり、測定結果ではない。

仕事の速度は初稿ではなく、依頼から利用可能な成果までで測る。作成時間だけ短縮しても、受け手の確認が増えれば改善とは呼ばない。

## 第2章 裁量を制する者は、世界を制す

AIが実行を担うほど、何を達成するか、どの情報を使うか、どこまで任せるかという判断の価値が上がる。

[Microsoftの2026年5月のWork Trend Index](https://www.microsoft.com/en-us/worklab/work-trend-index/agents-human-agency-and-the-opportunity-for-every-organization)では、先進的なAI活用層は、着手前にAIと人間の担当を意図的に切り分ける割合が53%（その他の層33%）、技能維持のため意図的にAIなしで作業する割合が43%（同30%）だった。いずれも自己申告による比較である。

依頼前に仕事を三つに分ける。

| 担当 | 判断基準 | 例 |
| --- | --- | --- |
| AI・既存ツールに委ねる | 入力、操作、必要な結果が明確 | 既存資料の検索、定型集計、限定的な実装 |
| 人間とAIが協働する | 選択肢や前提に不確実性がある | 仕様の比較、反例の探索、設計の採否 |
| 人間が担う | 認可、重大な利害、責任、技能維持に関わる | 公開の承認、顧客との合意、専門的な訓練 |

DORAが同じ2026年3月の分析で扱った熟練のパラドックスも、目先の処理速度と技能開発を同時に考える必要性を示す。AIの出力の誤りに気づく能力まで手放せば、委任範囲を適切に決められなくなる。

ただし、可逆で影響の小さい仕事まで人間の承認に戻せば、承認そのものがボトルネックになる。人間だけが決める必要のある判断と、すでに認可されている実行を分ける。裁量を守るとは、すべての判断を抱え込むことではない。

## 第3章 「完了条件先出し」はこうして必然になった

最初の時間で固めるのは、生成する文章量やコード量ではなく、仕事が終わる条件である。

[Claude Codeの公式ベストプラクティス](https://code.claude.com/docs/en/best-practices)は、エージェントに見えない前提を伝えること、結果を確かめる手段を与えること、例外を許さない制約を実行環境で強制することを推奨する。[Claude Agent SDKの公式解説](https://claude.com/resources/articles/building-agents-with-the-claude-agent-sdk)は、情報収集、実行、結果の確認、反復というエージェントの運用を説明している。

### 見えない前提だけを書く

既存コードにある仕様をプロンプトへ再転記しない。依頼者にしか分からない目的、制約、合格条件を既存Issueや仕様書へ置く。曖昧な要件は必要な分だけ対話で解消する。小さな変更なら一つのIssueや依頼文で足りる。

### 実行結果で完了を判定する

「修正しました」という文章ではなく、利用者が使う入口で何が変わったかを完了条件にする。必要なら既存のコマンド、型制約、テスト、プレビューなどを使う。確認手段は成果を届けるための手段であり、同じ実装をなぞるだけの検査や別の完了判定制度を増やす理由にはしない。

### 例外を許さない制約は実行境界で守る

秘密情報の読み取り、未承認の公開、本番データの破壊などは自然言語のお願いだけで防ぐのではなく、適用可能な権限設定や入力制約で守る。一方で、単なる好みまでフックや承認に変えれば、運用の摩擦が増える。

### 実際に起きたこと：813件のPRと現在地の問題

著者の[2026年8月の運用記録](https://github.com/KAFKA2306/articles/blob/639caef97c92177f2a3ea5eb3432f0683f3d4df8/articles/chatgpt-multiproject-autonomy.md)では、1か月間に813件のPRを作り686件をマージした。しかし123個の非forkリポジトリを横断すると、次に何をするべきか、マージを本番完了と呼べるかという判断が問題になった。

具体例は[finBI Issue #10](https://github.com/KAFKA2306/finBI/issues/10)である。取得時点では利用可能でなかったFRED DGS10の観測日・値がスナップショットに含まれたため、観測日だけでなく公開・取得可能だった時点を扱う必要が生じた。処理が成功してデータが出ることと、当時利用できたデータだけで分析できることは違う。

ここから採用する原則は、AIの生成速度を上げる前に、何を正しい成果とするかを定義することだ。既存の公開運用記録は判断上の問題が生じた事例であり、この方法による時間削減を測定した比較実験ではない。

## 第4章 今すぐ実践：小バッチと実行・修正ループ

[DORAの小バッチ作業ガイド](https://dora.dev/capabilities/working-in-small-batches/)は、AIによる巨大なPRがレビュー時の認知負荷を増やすことを指摘している。生成速度が上がっても、変更を理解し統合する能力が同じ速度で増えるとは限らない。

小バッチとは、行数やファイル数を機械的に制限することではない。目的が一つで、結果を理解でき、失敗時に元へ戻せる単位にすることである。不可分な変更を無理に分割して中間状態を壊すことは避ける。

今日から次の順序で仕事を進める。

1. 仕分け：成果、認可範囲、人間だけが決める事項を特定する。
2. 完了条件：利用者の入口、必要な入力、変わる結果、守る制約を既存の仕事の正本に書く。
3. 小バッチ実行：既存資料を取得し、一つの目的に必要な変更を実行する。失敗すれば原因を修正して再開する。
4. 反映：認可された利用先に届ける。残った障害と実行済みの範囲を区別し、同じ問題の再発を防ぐ必要最小限の知見を既存の正本へ戻す。

### 実践例：月次売上レポート

次は読者が自分の仕事へ移すための例であり、著者による実運用の測定ではない。

| 項目 | 具体的な依頼 |
| --- | --- |
| 目的 | 経営会議で先月の売上の増減を判断できるようにする |
| 入力 | 確定済み月次売上CSV、対象月、前年同月、単位 |
| 完了条件 | 既存の共有レポートに実績と前年同月比を反映し、出典を辿れる |
| 制約 | 元CSVを変更しない。欠落月や分母ゼロを売上ゼロと扱わない |
| 最初の実行 | まず1か月分を集計して既存レポートへ反映する |
| 失敗時 | 欠落した入力の取得を試みる。取得不能ならその範囲を明示し、捏造せず停止する |

毎回新しいレポート、監査台帳、承認手順を作る必要はない。既存の正本と実行入口を再利用し、同じ手順を次回から呼び出せるようにする。

DORAのラストマイルの分析が示すように、自社の業務文書、コード、データへの接続は重要だ。アクセス可能な一次情報を整備するほうが、毎回チャットに説明を貼り付ける運用より再開の摩擦を減らしやすい。

反例は、既存の小さな定型処理で入力と出力が明確な場合である。新たな仕様書も小バッチの計画も不要で、既存のCLIをそのまま実行するほうがよい。

## 第5章 トークンを燃やすな：作業量から成果と基盤へ

[DORAの2026年6月のtokenmaxxing論考](https://dora.dev/insights/finding-balance-in-the-era-of-tokenmaxxing/)は、トークン利用量がAI導入初期の試行を促し得る一方、消費量の競争を目的にすると、見せかけの生産性、低品質な生成物、心理的負担を招き得ると論じる。

残業時間を誇る代わりにトークンを誇るだけでは、評価の構造は変わらない。活動量が増えることと価値が増えることを分ける。

AI導入前後で比較するのは次の四点でよい。取得できる既存データを使い、計測のためだけの新しい報告業務は増やさない。

- 利用可能な成果：利用者の目的を達成した仕事。
- 到達時間：依頼から利用可能になるまでの経過時間。
- 人間の負担：判断、説明、修正、承認、再開にかかる時間。
- 維持負担：次回以降に必要な費用と運用作業。

[DORAの2025年レポート](https://dora.dev/dora-report-2025/)はAIを組織の強みと弱みを増幅する存在として捉えている。[AI Capabilities Model](https://dora.dev/ai/capabilities-model/report/)の七つの能力は、その増幅を成果へ変えるための基盤である。

| 基盤能力 | 実務での役割 |
| --- | --- |
| 利用者中心 | 作る理由を利用者の問題に結ぶ |
| バージョン管理 | 変更を安全に追跡・復旧できる |
| AIが参照できる社内データ | 業務固有の前提を再利用する |
| 小バッチ | 変更の理解と統合を容易にする |
| 共有されたAI方針 | 認可範囲と判断の迷いを減らす |
| 内部プラットフォーム | 定型的な環境・配布作業を吸収する |
| 健全なデータ基盤 | 誤った入力からの再作業を防ぐ |

自社の規模に合わない基盤を七つとも新設する必要はない。成果を阻害している箇所から一つずつ既存の仕組みを改善する。新しいAIツールを足す前に、不要なツールや重複経路を減らす。

## 第6章 個人の時間術から、引き継げる知能基盤へ

Microsoftの2026年Work Trend Indexでは、20,000人のAI利用者を対象とした自己申告調査を分析し、組織要因の相対的な重要度は67%、個人要因は32%だった。これは自己申告によるAI成果を説明する統計モデルの重要度であり、成果の67%が組織によって因果的に決まるという意味ではない。

同調査の先進的活用層は、AIに関する知見と失敗を共有する割合が61%（その他の層36%）、AI支援業務の品質基準を話し合う割合が54%（同29%）だった。エージェントの手順、引き継ぎ、品質基準が文書化され再現可能だと答えた割合は、チーム単位で26%対19%、部門単位で29%対17%、全社単位で25%対14%である。同社は組織固有の知見を蓄積し横展開する考え方をOwned Intelligenceと呼ぶ。[調査原典](https://www.microsoft.com/en-us/worklab/work-trend-index/agents-human-agency-and-the-opportunity-for-every-organization)

### モデルを交換しても仕事を再開できる構造にする

長期的に価値を持つのは、特定のモデル向けのプロンプト集だけではない。

| 残すもの | 正本の例 |
| --- | --- |
| 目的と完了条件 | MISSION、既存Issue、仕様 |
| 必要な一次情報と来歴 | コード、データ、公式資料 |
| 実行制約と引き継ぎ境界 | 権限設定、既存の実行契約 |
| 再利用できる知見と現在地 | Git履歴、既存Issue、利用先 |

著者が採用する[Kafstylerの使命](https://github.com/KAFKA2306/kafstyler/blob/007137cb1ba50aa1c1d5409b935a8e7616c252f6/MISSION.md)では、目的はMISSION、仕事はIssue、実装はGit、成果は利用先に置く。会話履歴に閉じ込めず、担当が変わっても既存の正本から再開する。上位モデルは難しい判断に、定型処理は既存CLIや低コストの実行主体に割り当てる。

重要なのは、次の仕事が前回より少ない説明と判断で進められることだ。解決するたびにプロンプト、管理台帳、承認、確認工程が増える仕組みでは、人間の負担が再び積み上がる。新しい知見を既存の正本や実行入口に統合し、不要になった経路を廃止する。

## おわりに：次の仕事で何を変えるか

次にAIへ仕事を任せるときは、最初に一文だけ書く。

> 誰が、どこで、何をできれば終わりか。

次に、既存の情報と実行入口を使わせ、必要な変更を小さく届ける。人間にしか決められない判断だけを引き受ける。失敗したら原因を解消し、再発する負担は既存の仕組みから取り除く。

この方法を採用しても、同等の成果に対する人間の総負担や到達時間が減らないなら、委任方法や仕組みを変えるべきだ。AIなしの既存処理のほうが速く確実な仕事もある。

ロケットスタートの目的は、昔も今も、仕事を早く終えて自分の時間を取り戻すことだ。AIが速くなったからといって、仕事を増やす必要はない。

**人間の自由を増やすことが目的であり、AIを動かし続けることは目的ではない。**
