「学ぶコストは下がった。でも、差は開いている。」

原稿を読んだ人には通じても、記事一覧でこの一文を見た人は「誰と誰の、何の差？」から考えることになります。AIに「短く」と頼んだはずが、読者に穴埋め問題を出している。

いる科さんは、この例を使って、文脈を補い、伝えたいことに順位を付け、筆者とAIのズレを直してから、タイトルを書き直す手順を紹介しています。題だけが先に見える記事やスライドなら、最後に「初見の読者が何を読み取れるか」まで確かめられます。 [いる科さんの投稿](https://x.com/iru_cection/status/2121705510319825086) · [投稿のミラー](https://teapawt.org/iru_cection/status/2121705510319825086)

## 短くする前に、原稿のどこを残すか決める

1. **省かれた文脈を戻す。** 本文を渡し、スライドなら筆者の台本も添える。文字数を気にせず「誰が、何を比べ、何について話すのか」を一文にする。原稿から補った内容と、推測で埋めた内容が分かるようにする。
2. **主張に優先順位を付ける。** AIに各主張の優先度を1〜10で付けさせ、理由と原稿の該当箇所を一緒に出す。10は「題で伝えたい主張」、6は「本文で補える背景」。点数は、どちらを題に残すつもりかを読み取る目安にする。
3. **順位が逆なら、言いたいことを伝え直す。** 下の例では、AIが「学ぶ手間が減った」を一番に選んだとしても、筆者が見せたいのは「無料版と有料版で学習直後の理解度を比べた結果」。そこで「題には比較対象と指標を入れる。手間の話は本文に置く」と伝える。定型の原稿なら、冒頭の目的文をこの指示に使える。
4. **表示場所に合わせて、題を一案作る。** 文字数はここで考える。比較を扱う記事一覧の題なら「無料版と有料版のAIで、学習直後の理解度を比較した」。導入スライドで問いを立てるなら「無料版と有料版のAIで、学習直後の理解度はどう違うか」。

題ができたら、原稿を渡していない別の会話で「この題は、何を比べて何を測る話か。一文で答えて」と頼みます。答えを筆者が一番に置いた主張と照らし合わせます。原稿を渡すのはその後です。本文まで読める状態だと、題から落ちた情報を本文で補えてしまいます。

## 同じ題材で、落ちる理由が二つある

以下は判定を試すための架空の原稿です。無料版と有料版のAIで同じ教材を学び、直後の理解度テストを比較したとします。測定は一時点です。

| 検査用の見出し | 読み取れる内容 | 判定 |
| --- | --- | --- |
| 学ぶコストは下がった。でも、差は開いている。 | 比較対象と指標が確定しない | 対象・指標を明示する |
| 無料版と有料版のAIで、理解度の差が広がった | 比較対象、指標、差の拡大 | 差の拡大には複数時点の証拠が要る |
| 無料版と有料版のAIで、学習直後の理解度を比較した | 比較対象、指標、測定時点 | 採用 |

二つ目は比較対象が明確でも、原稿より強い主張をしています。「差がある」と「差が広がった」では、要る証拠が違います。記事一覧なら題だけ、図と常に並ぶスライドなら図のラベルも含めて、実際に読者に見える範囲で確かめます。W3Cは見出しが内容の主題や目的を伝えることを求めています。技術発表のAssertion–Evidence方式では、一枚の主張を短い文で示し、図などで支えます。 [W3Cの見出し解説](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html) · [Assertion–Evidence](https://www.assertion-evidence.com/)

## 編集の判断を、採用条件に変える

下のコマンドは、原稿と見出しから抽出済みの判定項目を使う最小例です。JSONの各行は、上の表の順に対応します。曖昧な比較と、明確だが原稿を超えた主張が、別の理由で落ちることを再現できます。

```bash
jq -nc '
  inputs
  | {
      id,
      result: (
        if .subject_and_metric_recovered == false then "missing_comparison"
        elif .claims_widening and (.evidence_timepoints < 2) then "missing_time_series"
        elif .claims_widening then "check_trend"
        else "accept"
        end
      )
    }
' <<'EOF'
{"id":"ambiguous","subject_and_metric_recovered":false,"claims_widening":true,"evidence_timepoints":1}
{"id":"overclaim","subject_and_metric_recovered":true,"claims_widening":true,"evidence_timepoints":1}
{"id":"supported","subject_and_metric_recovered":true,"claims_widening":false,"evidence_timepoints":1}
EOF
```

この例では二時点未満なら「広がった」を棄却します。二時点以上なら照合に回し、対象の定義と測り方がそろい、差の増加を値で確認できた段階で採用します。

## 原稿と見出しを一行ずつ処理する

運用では、原稿・根拠位置・表示条件をJSONLで渡します。最初の呼び出しで主張に順位を付け、根拠を示します。原稿に目的文がある場合はそれを主題の判断に使い、候補を作ります。次の呼び出しには候補と実際の表示文言だけを渡して、読み戻した主題と比較項目を得ます。最後の照合には該当箇所だけを渡します。対象IDや時点数の一致はjqで処理し、言い換えや根拠の意味を照合するときだけモデルを使います。採用できた一案を標準出力に流し、保留の理由と根拠位置をJSONLに残します。

生成・評価の実行とJSON出力には、2026年公開のPromptfoo 0.125.1を使えます。同じ原稿セットで各手順の出力を比較できます。段間の受け渡しと集計は同年公開のjq 1.8.2に任せます。自作するのは媒体ごとの判定項目、対照例、シェルとjqのフィルターです。 [Promptfooリリース](https://github.com/promptfoo/promptfoo/releases/tag/0.125.1) · [評価結果の出力仕様](https://www.promptfoo.dev/docs/configuration/outputs/) · [jqのリリース記録](https://github.com/jqlang/jq/releases/tag/jq-1.8.2)

## トークン削減の前に、落とした理由を数える

「短くして」とだけ渡す現行手順を基準に、同じ原稿と表示条件で比べます。過去の採用題に、比較対象の削除、指標のすり替え、問いから断定への変更を一つずつ加えると、どの誤りを見逃したか確認できます。判定条件の調整に使った資料と、採否を決める資料は原稿単位で分けます。 [評価設計の公式ガイド](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

- **主題と比較の復元率**。題から戻せた主題、比較対象、指標を原稿と照合する。題が背景を中心にしていた場合は、順位付けと題のどちらでズレたかも記録する。モデルで読み戻した値は、読者理解の推定値として扱う。
- **重大な誤採用**。原稿を超える断定、因果、時系列を含む題の採用件数。回帰用の対照例では0件を合格条件にする。
- **採用率と採用1件あたりのトークン**。同じ入力集合で、採用件数と、生成・判定・再処理の総トークンを数える。復元率と採用率が現行以上の構成から、採用1件あたりの消費量が最少の構成を選ぶ。

手元の一枚で試すなら、筆者の「一番伝えたいこと」と、題だけを見た人の「何の話だと思ったか」を一文ずつ並べます。前者と後者がずれたら題を直す。二つが一致しても、題が原稿の根拠を超えていたら、言い切れる範囲まで戻します。
