「学ぶコストは下がった。でも、差は開いている。」この一文を見出しとして渡すと、「差」に入るのはAIの性能差かもしれないし、学習者の理解度の差かもしれません。「開いている」には、以前と比べて差が大きくなったという意味もあります。比較する相手を補うだけでは、後半の主張は検証できません。見出しの例は、いる科さんがXで紹介した文章を使いました。 [投稿の引用](https://teapawt.org/studio_yebisu?filter=posts)

スライドや技術記事の見出しを量産するときは、**表示される文言から主題が伝わるか**と、**その主張を原稿が支えるか**を別々に確かめます。この二つを分けると、どこを直せば出せるかが分かります。

## 同じ題材で、落ちる理由が二つある

以下は判定を試すための架空の原稿です。無料版と有料版のAIで同じ教材を学び、直後の理解度テストを比較したとします。測定は一時点です。

| 検査用の見出し | 読み取れる内容 | 判定 |
| --- | --- | --- |
| 学ぶコストは下がった。でも、差は開いている。 | 比較対象と指標が確定しない | 対象・指標を明示する |
| 無料版と有料版のAIで、理解度の差が広がった | 比較対象、指標、差の拡大 | 差の拡大には複数時点の証拠が要る |
| 無料版と有料版のAIで、学習直後の理解度を比較した | 比較対象、指標、測定時点 | 採用 |

一案だけ返すなら三つ目を使います。問題提起のスライドなら、原稿の役割に合わせて「無料版と有料版のAIで、学習直後の理解度はどう違うか」とできます。記事一覧では題だけ、図と常に並ぶスライドなら図のラベルまで渡し、読者が実際に見られる情報で判定します。W3Cは見出しが内容の主題や目的を伝えることを求めています。技術発表のAssertion–Evidence方式では、一枚の主張を短い文で示し、図などで支えます。 [W3Cの見出し解説](https://www.w3.org/WAI/WCAG22/Understanding/headings-and-labels.html) · [Assertion–Evidence](https://www.assertion-evidence.com/)

## 編集の判断を、採用条件に変える

書き手は、原稿から「何を伝える一枚か」と、その根拠の位置を取り出します。読み手側の確認では、原稿や生成時の説明を伏せ、表示される文言だけから主題を言い直します。比較なら対象と指標、差の拡大なら時系列の主張まで抽出します。最後に、読み取った内容を原稿に照合します。

下のコマンドは、原稿と見出しから抽出済みの判定項目を使う最小例です。JSONの各行は、上の表の順に対応します。曖昧な比較と、明確だが原稿を超えた主張が、別の理由で落ちることを再現できます。

```bash
jq -nc '
  inputs
  | {
      id,
      result: (
        if .subject_and_metric_recovered == false then "missing_comparison"
        elif .claims_widening and (.evidence_timepoints < 2) then "missing_time_series"
        elif .claims_widening then "check_trend"
        else "accept"
        end
      )
    }
' <<'EOF'
{"id":"ambiguous","subject_and_metric_recovered":false,"claims_widening":true,"evidence_timepoints":1}
{"id":"overclaim","subject_and_metric_recovered":true,"claims_widening":true,"evidence_timepoints":1}
{"id":"supported","subject_and_metric_recovered":true,"claims_widening":false,"evidence_timepoints":1}
EOF
```

この例では二時点未満なら「広がった」を棄却します。二時点以上なら照合に回し、対象の定義と測り方がそろい、差の増加を値で確認できた段階で採用します。

## 原稿と見出しを一行ずつ処理する

運用では、原稿・根拠位置・表示条件をJSONLで渡します。最初の呼び出しで主題と根拠を取り出し、候補を作ります。次の呼び出しには候補と実際の表示文言だけを渡して、読み戻した主題と比較項目を得ます。最後の照合には該当箇所だけを渡します。対象IDや時点数の一致はjqで処理し、言い換えや根拠の意味を照合するときだけモデルを使います。採用できた一案を標準出力に流し、保留の理由と根拠位置をJSONLに残します。

生成・評価の実行とJSON出力には、2026年公開のPromptfoo 0.125.1を使えます。0.125系には反復実行の安定性と、キャッシュが使われた行を集計する機能があります。段間の受け渡しと集計は同年公開のjq 1.8.2に任せます。自作するのは媒体ごとの判定項目、対照例、シェルとjqのフィルターです。 [Promptfooリリース](https://github.com/promptfoo/promptfoo/releases) · [評価結果の出力仕様](https://www.promptfoo.dev/docs/configuration/outputs/) · [jqのリリース記録](https://jqlang.org/)

## トークン削減の前に、落とした理由を数える

「短くして」とだけ渡す現行手順を基準に、同じ原稿と表示条件で比べます。過去の採用題に、比較対象の削除、指標のすり替え、問いから断定への変更を一つずつ加えると、どの誤りを見逃したか確認できます。判定条件の調整に使った資料と、採否を決める資料は原稿単位で分けます。 [評価設計の公式ガイド](https://developers.openai.com/api/docs/guides/evaluation-best-practices)

- **主題と比較の復元率**。題から戻せた主題、比較対象、指標を原稿と照合する。モデルで読み戻した値は、読者理解の推定値として扱う。
- **重大な誤採用**。原稿を超える断定、因果、時系列を含む題の採用件数。回帰用の対照例では0件を合格条件にする。
- **採用率と採用1件あたりのトークン**。同じ入力集合で、採用件数と、生成・判定・再処理の総トークンを数える。復元率と採用率が現行以上の構成から、採用1件あたりの消費量が最少の構成を選ぶ。

この手順は、題やラベルだけが先に表示され、読者が次に何を読むか決める場面にも使えます。手元の見出しで試すなら、まず題を見える範囲だけに切り出し、「何を比べ、何を測り、どこまで言っているか」を一文に戻します。その一文を支える箇所が本文にあるか確かめると、題を変えるか、本文に証拠を足すか決められます。
