# 「最初から分かっていた」を防ぐには？ 暴落で買った3日をLLMとGitで検証する

結果を知ったあとなら、理由はいくらでもきれいに説明できる。

「あの時点で分かっていた」

「この材料を見て判断した」

「最初からこのシナリオだった」

でも、本当にそうだったのか。

これは投資に限らない。

障害対応、研究、採用、企画、スポーツ、旅行。人間が不確実な状況で判断する仕事には、だいたい同じ問題がある。

**結果を知った瞬間から、過去の自分の思考まで少しずつ書き換わる。**

ソフトウェアならGitで「その時点のコード」を残せる。

実験なら条件と結果を分けて記録できる。

では、**人間の判断そのものも、あとから検証できる形にできないか。**

この記事では、その題材として自分の2026年の投資を使う。

手元の口座明細で確認できる範囲では、NF日経半導体株（200A）を次の3日に買っている。

| 日付 | 買付単価 |
|---|---:|
| 4月1日 | 2,992円 |
| 4月6日 | 3,080円 |
| 7月29日 | 3,601円 |

数量は公開しない。

後からチャートだけを見ると、「暴落の底をうまく買った」という話にできる。

でも、それでは面白くない。

知りたいのは、

> **当時の情報だけをもう一度渡されたとき、なぜその判断になったのかを再生できるか**

である。

結論から言うと、自分が見ていたものは3つだった。

1. **実体は本当に壊れたのか**
2. **売りは実体悪化だけで説明できるのか**
3. **自分が間違う弱気ケースでも安いのか**

**3つ全部を通過しなければ買わない。**

そして後から振り返るために、LLMで思考を分解し、Gitでその時点の版を残す。

この記事は「AIに何を買うか聞く方法」ではない。

**人間の曖昧な判断を、あとから反証できる形にする方法**について書く。

> これは私自身の売買判断の記録であり、特定銘柄の売買を勧めるものではありません。

## 4月：悪い未来に必要な条件が、本当に揃っているか

4月の判断は、4月になって突然始まったものではない。

### 3月17日：ホルムズ海峡を「市場の物理制約」として見ていた

`yt3` のGit履歴には、3月17日付の分析が**遅くとも3月27日時点**で保存されている。

固定スナップショット：

https://github.com/KAFKA2306/yt3/blob/b5cecf13efd4b40cb53a97b4950db5dc353ba5ba/data/memory/essences.json

そのcommit：

https://github.com/KAFKA2306/yt3/commit/b5cecf13efd4b40cb53a97b4950db5dc353ba5ba

ここで重要なのは、memory内の個々の数値を現在の事実として採用することではない。

証拠として使うのは一つだけだ。

> **4月の買付より前から、地政学を「ニュース」ではなく、物流・供給・価格を制約する現実として考えていた。**

結果を知った後の記事だけなら、いくらでも綺麗な物語を作れる。

しかしcommit SHAを固定すると、少なくとも**その時点でリポジトリに存在した版**を後から読み返せる。

### 現実：軍事作戦そのものは本物だった

これは「戦争なんて大したことはない」と楽観して買った取引ではない。

米中央軍はOperation Epic Furyを公式に記録している。

https://www.centcom.mil/OPERATIONS-AND-EXERCISES/EPIC-FURY/

自分が疑ったのは軍事リスクそのものではなく、**市場がさらに先まで織り込んでいる悪化シナリオ**だった。

### 3月31日〜4月1日：言葉ではなく「必要な行動」を見る

当時の自分のログには、こう残っている。

> 3月31日　「ホルムズ海峡を諦めたんじゃないの」
>
> 4月1日 9:22　「アメリカ陸軍なにしに派遣したんだ」
>
> 4月1日 11:36　「ピクニック了解」

言葉はかなり雑だ。

でも、考えていたことは単純だった。

**さらに大きな戦争をするなら、それに必要な兵力・配置・補給・政治的意思が現実に現れるはずだ。**

つまり、

> 市場が恐れている未来

から逆算して、

> その未来を実現するために必要な条件

を現実側で探した。

必要条件が足りないなら、価格が悪い未来を強く織り込みすぎている可能性がある。

4月1日に買った。

### 同じ4月1日：「分からんかった」と自分の因果を修正した

同日11:36には、こんなメモも残っている。

> 「ホルムズ海峡締まったままでも終戦したら日経上がるんだ。分からんかった。」

この一文は、成功談としては格好が悪い。

だからこそ残す価値がある。

自分は当初、ホルムズ海峡の閉鎖そのものをかなり重く見ていた。

しかし市場は、海峡が直ちに正常化しなくても、

- 長期戦リスクが下がる
- 海峡を強制開放する追加軍事作戦の可能性が下がる
- 戦争全体の不確実性が下がる

ことを先に評価した。

**価格を観測して、自分の因果モデルも更新した。**

### 4月2日：自分に都合の悪い材料も出た

翌日の公式演説は、単純な終戦宣言ではなかった。

ホワイトハウスの記録では、軍事目標は近く達成されるとの説明と同時に、今後2〜3週間は強い攻撃を続けるという発言も含まれていた。

https://www.whitehouse.gov/releases/2026/04/president-trump-delivers-powerful-primetime-address-on-operation-epic-fury/

当時の自分も、

> 4月2日 11:47　「tacoやろ」

と、期待していたほど素直なde-escalationではないことを認識している。

さらに15:28には、演説内容の多くが既出情報の繰り返しではないか、と見直している。

4月1日に買った後で、都合のいい情報だけを集めたわけではない。

**反対材料が出れば、仮説を更新した。**

4月6日にもう一度買った。

### 4月8日：その後の結果

4月8日、ホワイトハウスは停戦とホルムズ海峡再開への合意を発表した。

https://www.whitehouse.gov/releases/2026/04/peace-through-strength-operation-epic-fury-crushes-iranian-threat-as-ceasefire-takes-hold/

これは結果として自分の買い判断に有利だった。

ただし、4月8日の結果から逆算して「4月1日に停戦を予言していた」とは考えない。

再現したいのは予言ではなく、次の手順だ。

> **悪い未来が価格に入っているなら、その未来を実現するための必要条件を現実側で探す。条件が不足していれば価格を疑う。反対材料が出れば仮説を更新する。**

これが4月の抽象だ。

## 7月：企業価値と、売り手の事情を分ける

7月は同じ考え方を企業に使った。

分析の中心に置いていたのはキオクシアだった。

一方、手元の口座明細で今回確認できる7月29日の執行は、NF日経半導体株（200A）の3,601円での買付である。

**分析対象と実際の執行対象は分けて記録する。**

### 7月29日：「営業利益」「信用」「安い」を別々に見た

当日の自分のログには、数時間のうちに次の記録がある。

> 12:25　「営業利益でるはず」
>
> 12:40　「信用買いの強制整理が進んでいるが、まだ整理完了とはいえない」
>
> 18:09　「やっす」
>
> 18:09　「予想PER三倍台？」
>
> 18:09　「信用　焼けてきた」

ここでも、雑なメモをそのまま事実扱いしてはいけない。

「信用買いの強制整理」は、当時置いた**需給仮説**である。

JPXの公開データから信用残の変化は確認できても、追証や強制決済が実際に何株発生したかまでは直接分からない。

https://www.jpx.co.jp/markets/statistics-equities/margin/05.html

https://www.jpx.co.jp/markets/statistics-equities/margin/index.html

また、「予想PER三倍台？」は、**キオクシアについて当時置いた私的な利益シナリオからの概算**である。

ETFのPERでも、会社予想でもない。

この日の判断を分解すると、こうなる。

1. **実体**：利益は本当に崩れるのか
2. **売り手**：下落は企業価値の悪化だけで説明できるのか
3. **価格**：自分の利益予想を弱くしてもまだ安いのか

**株価が下がったから安い、ではない。**

### 7月30日：結果を見る前に、仮説と棄却条件を固定した

翌7月30日、決算前の分析をGitHubへ残した。

固定スナップショット：

https://github.com/KAFKA2306/semiconductor-earnings-model/blob/04590b68e6f4ec6e5ff0a41af50ddd363a57f074/docs/reports/semiconductor/2026-07-30-kioxia-nand-sector-capex.md

そのcommit：

https://github.com/KAFKA2306/semiconductor-earnings-model/commit/04590b68e6f4ec6e5ff0a41af50ddd363a57f074

この時点で情報を、

- 会社開示
- 作業仮定
- 推論
- 未確認

に分けている。

さらに結果を見る前に、

- 継続強気
- WATCH
- 仮説棄却

の条件を書いた。

たとえば、ASPと利益率が同時に悪化する、データセンター向け出荷が計画未達になる、在庫増加とフリーキャッシュフロー悪化が同時に起こる、といった条件なら仮説を捨てる設計だった。

ここでGitが効く。

**結果を見る前の仮説と、結果を見た後の評価を別の版にする。**

そうすると「最初から分かっていた気がする」をdiffで壊せる。

### 7月31日：実体側は強かった

翌日の会社発表では、2027年3月期第1四半期の売上収益は約1兆7,671億円、営業利益は約1兆2,700億円、親会社株主に帰属する利益は約8,422億円だった。

会社は増収の主因として、生成AIを中心とするデータセンター顧客の強い需要を背景にしたASPの大幅上昇を挙げている。

https://ssl4.eir-parts.net/doc/285A/tdnet/2859908/00.pdf

これは「利益は本当に崩れるのか」という実体側の問いには強い答えだった。

一方で、**決算は「信用買いの強制整理が下落の主因だった」という需給仮説までは証明しない。**

そこは今も仮説として残す。

7月の抽象はこれだ。

> **企業が悪いから売られているのか、売り手が売らなければならないから下がっているのかを分ける。**

## ここまでを一般化すると、判断には3つのゲートがあった

4月は地政学。

7月は半導体。

対象は全く違う。

それでも、判断は同じ3つの問いにできた。

### Gate 1：実体は壊れたか

4月なら、さらに戦争を拡大するための現実の条件を見る。

7月なら、需要・ASP・利益・財務を見る。

**YESなら買わない。**

まず現実を見る。

### Gate 2：売りは実体悪化だけで説明できるか

悪化した現実を正しく織り込んでいるだけなら、単なる適正な価格調整かもしれない。

一方で、恐怖、レバレッジ解消、信用整理、イベント前後のポジション整理など、価値とは別の事情が売りを増幅することもある。

**YESなら買わない。**

価格だけでなく、売り手を見る。

### Gate 3：自分が間違う弱気ケースでも安いか

強気シナリオが全部当たらなければ成立しない投資はしない。

利益予想が外れる。

反発まで時間がかかる。

想定した改善が一部しか起きない。

それでも安いかを見る。

**NOなら買わない。**

3つを短くすると、

> **実体を見る。売り手を見る。弱気でも安いときだけ買う。**

になる。

擬似コードにすると、これだけだ。

```python
if fundamentals_broken:
    return "PASS"

if selling_is_explained_by_fundamentals:
    return "PASS"

if not cheap_even_in_bear_case:
    return "PASS"

return "BUY_CANDIDATE"
```

暴落は買い理由ではない。

良い決算も買い理由ではない。

もう一段抽象化すると、

> **今の価格が成立するために必要な「悪い世界」を逆算する。その世界が現実には成立しにくく、別の理由で売りが集中し、しかも弱気に見ても安いときだけ買う。**

となる。

未来の好材料を当てることが中心ではない。

**価格が暗黙に仮定している未来と、現実の制約の矛盾を探す。**

## では、LLMとGitは何のために使うのか

ここまでなら、LLMもGitもなくても考えられる。

問題は、**あとから本当に同じ説明をしていたのか確認できない**ことだ。

そこで技術を使う。

```text
一次資料・市場データ・自分の生ログ
              ↓
        その時点の観測
              ↓
      LLMで論点を分解
  観測 / 仮説 / 反証条件 / 未確認
              ↓
       Markdownで記録
              ↓
          git commit
              ↓
       後日、結果とdiff
```

### LLMは「答えを出す」のではなく、思考をlintする

自分が欲しいのは、LLMの「買いです」「売りです」という結論ではない。

欲しいのは、**自分の思考の分解と反証**だ。

たとえば、判断前のメモを渡すなら、こう聞く。

```text
この時点で利用可能な情報だけを使って整理して。

1. 観測できた事実
2. 私が置いている仮説
3. 事実ではなく推論に過ぎない部分
4. この仮説を棄却する条件
5. まだ確認できていない情報

結論を強くしすぎず、観測と推論を混ぜないこと。
```

「信用が焼けている」という一言も、

> 信用残の減少は観測できる。ただし強制決済株数そのものは観測できない。したがって「レバレッジ解消が下落を増幅した」は仮説。

まで分解できる。

**LLMをアルファ生成器ではなく、思考のlintとして使う。**

### Gitはコードではなく「当時の自分」をversioningする

最低限、判断時点で次のMarkdownをcommitする。

```markdown
# Decision Log

observed_at: 2026-07-30 12:00 JST
status: WATCH

## 観測
- ...

## 仮説
- ...

## 価格が暗黙に置いている悪いシナリオ
- ...

## 反証条件
- ...

## 未確認
- ...

## 判断
- BUY / WATCH / PASS
```

結果が出ても、このファイルを「正しかった形」に書き換えない。

後日の評価は別commit、あるいは別セクションとして追加する。

記事から参照するときは `main` ではなく、**commit SHAを含む固定URL**を使う。

Gitは正解を保証しない。

でも、**いつ何を考えていたかを後から別物にしてしまうことは難しくできる。**

## 実は、定量研究でも同じことをしていた

ここで、自分の別の投資研究プロジェクトを見ると面白い。

`KAFKA2306/investor` では、投資研究の情報を最初から、

- 公式fact
- 派生値
- 推定・予測
- 人間またはLLMによる解釈
- 注文・約定などの執行証拠

に分けている。

https://github.com/KAFKA2306/investor

さらにAAARTS（`KAFKA2306/investor2`）では、定量的な投資仮説を次の順で扱っている。

```text
一次情報
  ↓
仮説を登録
  ↓
その時点で利用可能だったデータを固定
  ↓
バックテスト
  ↓
未来期間を触らずにOOS検証
  ↓
再現可能な証拠を残す
  ↓
採択 / 棄却 / 保留
  ↓
最後は人間が判断
```

https://github.com/KAFKA2306/investor2

正準フロー：

https://github.com/KAFKA2306/investor2/blob/main/docs/architecture/canonical-investment-flow.md

AAARTSでは、バックテストが良かっただけでは仮説を昇格させない。

未来情報の混入、OOS、取引費用、頑健性、反証条件を見る。

LLMについても、まずLLMなしのbaselineを測り、その後にLLMを追加し、**同じ未使用期間で本当に増分があるか**を比較する。

https://github.com/KAFKA2306/investor2/blob/main/docs/specs/time_tested_alpha_policy.md

ここで気づいた。

> **定量研究ではモデルをGit管理して反証していた。裁量投資では、自分の思考をGit管理して反証すればいい。**

両者はかなり似ている。

| 定量研究 | 裁量判断 |
|---|---|
| point-in-time data | その時点で見えていた一次資料 |
| hypothesis | 自分の仮説 |
| frozen OOS | 結果を見る前に固定した反証条件 |
| evidence artifact | Gitに残したDecision Log |
| reject / promote | PASS / BUY候補 / 仮説棄却 |
| model review | 後日の自分の判断レビュー |

もちろん、裁量判断をOOS検証と同一視するわけではない。

重要なのは、**結果を見る前に条件を固定し、結果が悪くても記録を消さない**という研究姿勢が共通していることだ。

AAARTSでは、実際に複数の古典的な投資仮説を検証して、追加した7仮説がすべて確認ゲートを通らなかった結果もそのまま残している。

https://github.com/KAFKA2306/investor2/blob/main/docs/research/multi_paper_oos_summary.md

成功例だけを残す仕組みではない。

これは裁量判断でも同じにしたい。

## この方法にも弱点がある

LLMとGitを使えば正しく判断できる、という話ではない。

特に間違いやすいのは次の3点だ。

- 実体悪化を「一時的な売り」と誤認する
- 売り手の事情を観測できないのに、強制売却だと決めつける
- 自分の強気な利益予想を「弱気ケース」と呼んでしまう

LLMは自信満々に間違える。

与えた情報が偏っていれば、綺麗に偏った結論を返す。

Gitも、間違った仮説を正しくするわけではない。

だから、

> **観測事実と仮説を分ける。反証条件を先に書く。結果前の版を残す。失敗も消さない。**

という使い方をする。

## 再現したいのは「正解」ではなく、判断プロセス

後から頭の中を完全に復元することはできない。

だから、判断した時点で次の5つだけ残す。

1. **観測** — その時点で確認できた事実
2. **仮説** — 何が起きていると思ったか
3. **反証条件** — 何が起きたら見方を捨てるか
4. **判断** — BUY / WATCH / PASS
5. **答え合わせ** — 後日、何が当たり何が外れたか

これは投資以外でも使える。

研究なら「この実験結果が出なければ仮説を捨てる」。

障害対応なら「このログが出れば原因A、出なければAを捨てる」。

企画なら「このKPIが動かなければ仮説を見直す」。

大事なのは、**結果を知る前の自分を残しておくこと**だ。

自分の場合、それを投資でやったら、4月と7月の判断が同じ3ゲートに整理できた。

底値を再現したいわけではない。

> **価格と現実のずれを見つける手順を再現したい。**

そして、もっと一般化すれば、

> **LLMで思考をlintして、Gitで判断をversioningする。**

という話になる。

「勘が当たった」で終わるより、その方がずっと検証しやすい。
