# 暴落でなぜ買えたのか？ LLMとGitで裁量判断を3つのゲートにした

2026年、手元の口座明細で確認できる範囲では、NF日経半導体株（200A）を次の3日に買っている。

| 日付 | 買付単価 |
|---|---:|
| 4月1日 | 2,992円 |
| 4月6日 | 3,080円 |
| 7月29日 | 3,601円 |

数量は公開しない。

後からチャートを見ると、かなり大きく売られた局面で買えている。

でも、自分がやっていたのは底値当てではない。

見るものは3つだけだった。

1. **実体は本当に壊れたのか**
2. **売りは実体悪化だけで説明できるのか**
3. **自分が間違う弱気ケースでも安いのか**

**3つ全部を通過しなければ買わない。**

普段は何もしない。

> **良いものを買うのではない。実体が壊れていないのに、別の理由で売られ、自分が間違っても安いときだけ買う。**

この記事で書きたいのは投資の成功談だけではない。

**人間の裁量判断を、LLMで分解し、Gitで履歴を残し、あとから反証できる形にする方法**について書く。

LLMに「何を買えばいい？」と聞く話ではない。

GitHubを売買シグナルにする話でもない。

役割はもっと地味だ。

```text
一次資料・市場データ・自分の生ログ
              ↓
      LLMで論点を分解する
  観測 / 仮説 / 反証条件 / 未確認
              ↓
       Markdownで記録する
              ↓
          git commit
              ↓
      後日、結果とdiffを見る
```

**LLMは予言者ではなく、思考を分解する道具。Gitは正解を保証する道具ではなく、当時の版を残す道具。**

この組み合わせで、後知恵を少し減らせる。

> これは私自身の売買判断の記録であり、特定銘柄の売買を勧めるものではありません。

## 4月：悪い未来に必要な条件が、本当に揃っているか

4月の判断は、4月になって突然始まったものではない。

### 3月17日：ホルムズ海峡を「市場の物理制約」として見ていた

`yt3` のGit履歴には、3月17日付の分析が**遅くとも3月27日時点**で保存されている。

固定スナップショット：

https://github.com/KAFKA2306/yt3/blob/b5cecf13efd4b40cb53a97b4950db5dc353ba5ba/data/memory/essences.json

そのcommit：

https://github.com/KAFKA2306/yt3/commit/b5cecf13efd4b40cb53a97b4950db5dc353ba5ba

ここで重要なのは、memory内の個々の数値を現在の事実として採用することではない。

証拠として使うのは一つだけだ。

> **4月の買付より前から、地政学を「ニュース」ではなく、物流・供給・価格を制約する現実として考えていた。**

これはGitで履歴を残すメリットでもある。

結果を知った後の記事だけを読めば、いくらでも綺麗な物語を作れる。

しかしcommit SHAを固定すると、少なくとも**その時点でリポジトリに存在した版**を後から読み返せる。

### 現実：軍事作戦そのものは本物だった

これは「戦争なんて大したことはない」と楽観して買った取引ではない。

米中央軍はOperation Epic Furyを公式に記録している。

https://www.centcom.mil/OPERATIONS-AND-EXERCISES/EPIC-FURY/

自分が疑ったのは、軍事リスクそのものではなく、**市場がさらに先まで織り込んでいる悪化シナリオ**だった。

### 3月31日〜4月1日：言葉ではなく「必要な行動」を見る

当時の自分のログには、こう残っている。

> 3月31日　「ホルムズ海峡を諦めたんじゃないの」
>
> 4月1日 9:22　「アメリカ陸軍なにしに派遣したんだ」
>
> 4月1日 11:36　「ピクニック了解」

言葉は雑だが、考えていたことは単純だった。

**さらに大きな戦争をするなら、それに必要な兵力・配置・補給・政治的意思が現実に現れるはずだ。**

つまり、

> 市場が恐れている未来

から逆算して、

> その未来を実現するために必要な条件

を現実側で探した。

必要条件が足りないなら、悪い未来を強く織り込みすぎている可能性がある。

4月1日に買った。

### 同じ4月1日：価格を見て、自分の因果も修正した

同日11:36には、次のメモも残している。

> 「ホルムズ海峡締まったままでも終戦したら日経上がるんだ。分からんかった。」

ここは重要だった。

自分は当初、ホルムズ海峡の閉鎖そのものをかなり重く見ていた。

しかし市場は、海峡が直ちに正常化しなくても、

- 長期戦リスクが下がる
- 海峡を強制開放する追加軍事作戦の可能性が下がる
- 戦争全体の不確実性が下がる

ことを先に評価した。

**価格を観測して、自分の因果モデルも更新した。**

### 4月2日：自分に都合の悪い材料も出た

翌日の公式演説は、単純な終戦宣言ではなかった。

ホワイトハウスの記録では、軍事目標は近く達成されるとの説明と同時に、今後2〜3週間は強い攻撃を続けるという発言も含まれていた。

https://www.whitehouse.gov/releases/2026/04/president-trump-delivers-powerful-primetime-address-on-operation-epic-fury/

当時の自分も、

> 4月2日 11:47　「tacoやろ」

と、期待していたほど素直なde-escalationではないことを認識している。

さらに15:28には、演説内容の多くが既出情報の繰り返しではないか、と見直している。

つまり、4月1日に買った後で、都合のいい情報だけを集めたわけではない。

**反対材料が出れば、仮説を更新した。**

4月6日にもう一度買った。

### 4月8日：その後の結果

4月8日、ホワイトハウスは停戦とホルムズ海峡再開への合意を発表した。

https://www.whitehouse.gov/releases/2026/04/peace-through-strength-operation-epic-fury-crushes-iranian-threat-as-ceasefire-takes-hold/

これは結果として自分の買い判断に有利だった。

ただし、4月8日の結果から逆算して「4月1日に停戦を予言していた」とは考えない。

再現したいのは予言ではなく、次の手順だ。

> **悪い未来が価格に入っているなら、その未来を実現するための必要条件を現実側で探す。条件が不足していれば価格を疑う。反対材料が出れば仮説を更新する。**

これが4月の抽象だ。

## 7月：企業価値と、売り手の事情を分ける

7月は同じ考え方を企業に使った。

分析の中心に置いていたのはキオクシアだった。

一方、手元の口座明細で今回確認できる7月29日の執行は、NF日経半導体株（200A）の3,601円での買付である。

**分析対象と実際の執行対象は分けて記録する。**

### 7月29日：実体・売り手・価格を別々に見る

当日の自分のログには、数時間のうちに次の記録がある。

> 12:25　「営業利益でるはず」
>
> 12:40　「信用買いの強制整理が進んでいるが、まだ整理完了とはいえない」
>
> 18:09　「やっす」
>
> 18:09　「予想PER三倍台？」
>
> 18:09　「信用　焼けてきた」

ただし、ここでは事実と仮説を分ける必要がある。

「信用買いの強制整理」は、当時置いた**需給仮説**である。

JPXの公開データから信用残の変化は確認できても、追証や強制決済が実際に何株発生したかまでは直接分からない。

https://www.jpx.co.jp/markets/statistics-equities/margin/05.html

https://www.jpx.co.jp/markets/statistics-equities/margin/index.html

また、「予想PER三倍台？」は、**キオクシアについて当時置いた私的な利益シナリオからの概算**である。

ETFのPERでも、会社予想でもない。

この日の判断を分解すると、こうなる。

1. **実体**：利益は本当に崩れるのか
2. **売り手**：下落は企業価値の悪化だけで説明できるのか
3. **価格**：自分の利益予想を弱くしてもまだ安いのか

**株価が下がったから安い、ではない。**

### 7月30日：決算前に仮説と反証条件をGitで固定した

翌7月30日、決算前の分析をGitHubへ残した。

固定スナップショット：

https://github.com/KAFKA2306/semiconductor-earnings-model/blob/04590b68e6f4ec6e5ff0a41af50ddd363a57f074/docs/reports/semiconductor/2026-07-30-kioxia-nand-sector-capex.md

そのcommit：

https://github.com/KAFKA2306/semiconductor-earnings-model/commit/04590b68e6f4ec6e5ff0a41af50ddd363a57f074

この時点で情報を、

- 会社開示
- 作業仮定
- 推論
- 未確認

に分けている。

さらに結果を見る前に、

- 継続強気
- WATCH
- 仮説棄却

の条件を書いた。

たとえば、ASPと利益率が同時に悪化する、データセンター向け出荷が計画未達になる、在庫増加とフリーキャッシュフロー悪化が同時に起こる、といった条件なら仮説を捨てる設計だった。

ここは、投資判断をGit管理する意味が最も分かりやすい。

**結果を見る前の仮説と、結果を見た後の評価を別commitにする。**

そうすると「最初から分かっていた気がする」をdiffで壊せる。

### 7月31日：実体側は強かった

翌日の会社発表では、2027年3月期第1四半期の売上収益は約1兆7,671億円、営業利益は約1兆2,700億円、親会社株主に帰属する利益は約8,422億円だった。

会社は増収の主因として、生成AIを中心とするデータセンター顧客の強い需要を背景にしたASPの大幅上昇を挙げている。

https://ssl4.eir-parts.net/doc/285A/tdnet/2859908/00.pdf

これは「利益は本当に崩れるのか」という実体側の問いには強い答えだった。

一方で、**決算は「信用買いの強制整理が下落の主因だった」という需給仮説までは証明しない。**

そこは今も仮説として残す。

7月の抽象はこれだ。

> **企業が悪いから売られているのか、売り手が売らなければならないから下がっているのかを分ける。**

## LLMに投資判断をさせない

ここでLLMの役割をはっきりさせる。

自分が欲しいのは、LLMの「買いです」「売りです」という結論ではない。

欲しいのは、**自分の思考の分解と反証**だ。

たとえば、判断前のメモを渡すなら、こう聞く。

```text
この時点で利用可能な情報だけを使って整理して。

1. 観測できた事実
2. 私が置いている仮説
3. 事実ではなく推論に過ぎない部分
4. この仮説を棄却する条件
5. まだ確認できていない情報

結論を強くしすぎず、観測と推論を混ぜないこと。
```

これだけでも、

> 「信用が焼けている」

という雑な一言を、

> 信用残の減少は観測できる。ただし強制決済株数そのものは観測できない。したがって「レバレッジ解消が下落を増幅した」は仮説。

まで分解できる。

**LLMをアルファ生成器ではなく、思考のlintとして使う。**

この使い方なら、モデルが賢くなっても役割が変わりにくい。

## Gitで「当時の自分」を残す

LLMだけでは再現性が弱い。

会話は後から要約できるし、人間も結果を知ると記憶を書き換える。

そこでGitを使う。

最低限、判断時点で次のMarkdownをcommitする。

```markdown
# Decision Log

observed_at: 2026-07-30 12:00 JST
status: WATCH

## 観測
- ...

## 仮説
- ...

## 価格が暗黙に置いている悪いシナリオ
- ...

## 反証条件
- ...

## 未確認
- ...

## 判断
- BUY / WATCH / PASS
```

結果が出ても、このファイルを「正しかった形」に書き換えない。

後日の評価は別commit、あるいは別セクションとして追加する。

そして記事から参照するときは `main` ではなく、**commit SHAを含む固定URL**を使う。

これでGitは、単なるコード管理ではなく、**意思決定のバージョン管理**になる。

## 4月と7月は、対象が違うだけで同じだった

4月は地政学。

7月は半導体。

対象は違うが、判断は同じ3ゲートにできる。

## Gate 1：実体は壊れたか

4月なら、さらに戦争を拡大するための現実の条件を見る。

7月なら、需要・ASP・利益・財務を見る。

**YESなら買わない。**

ニュースや株価ではなく、まず現実を見る。

## Gate 2：売りは実体悪化だけで説明できるか

企業価値やマクロ環境が悪化したから売られているなら、それは単なる適正な価格調整かもしれない。

一方で、恐怖、レバレッジ解消、信用整理、イベント前後のポジション整理など、価値とは別の事情が売りを増幅している可能性もある。

**YESなら買わない。**

価格だけでなく、売り手を見る。

## Gate 3：自分が間違う弱気ケースでも安いか

強気シナリオが全部当たらなければ成立しない投資はしない。

利益予想が外れる。

反発まで時間がかかる。

想定した改善が一部しか起きない。

それでも安いかを見る。

**NOなら買わない。**

## 3つ全部を通過したときだけ買う

まとめると、

- Gate 1：実体は壊れていない
- Gate 2：売りは実体悪化だけでは説明できない
- Gate 3：弱気ケースでも安い

この3つが同時に成立したときだけ参加する。

一つでも欠けたらPASSする。

擬似コードにすると、これだけだ。

```python
if fundamentals_broken:
    return "PASS"

if selling_is_explained_by_fundamentals:
    return "PASS"

if not cheap_even_in_bear_case:
    return "PASS"

return "BUY_CANDIDATE"
```

暴落は買い理由ではない。

良い決算も買い理由ではない。

> **実体を見る。売り手を見る。弱気でも安いときだけ買う。**

これが自分のスタイルを最も短く書いた形だ。

もう一段抽象化すると、こうなる。

> **今の価格が成立するために必要な「悪い世界」を逆算する。その世界が現実には成立しにくく、別の理由で売りが集中し、しかも弱気に見ても安いときだけ買う。**

未来の好材料を当てることが中心ではない。

**価格が暗黙に仮定している未来と、現実の制約の矛盾を探す。**

## この方法にも弱点がある

この方法は、安いものを自動的に見つける公式ではない。

特に間違いやすいのは次の3点だ。

- 実体悪化を「一時的な売り」と誤認する
- 売り手の事情を観測できないのに、強制売却だと決めつける
- 自分の強気な利益予想を「弱気ケース」と呼んでしまう

LLMを使っても、この問題は消えない。

LLMは自信満々に間違えるし、与えた情報が偏っていれば綺麗に偏った結論を返す。

だから、**観測事実と仮説を分け、反証条件を先に書き、結果前の版をGitに残す。**

## 再現したいのは底値ではなく、判断プロセス

後から頭の中を完全に復元することはできない。

だから、判断した時点で次の5つだけ残す。

1. **観測** — その時点で確認できた事実
2. **仮説** — 何が価格を動かしていると思ったか
3. **反証条件** — 何が起きたら見方を捨てるか
4. **判断** — BUY / WATCH / PASS
5. **答え合わせ** — 後日、何が当たり何が外れたか

一次資料とGit履歴を残しておけば、後から**当時の情報だけで判断を再生できる。**

7月30日の決算前コミットがその一例になった。

4月についても、少なくとも3月27日時点のGit履歴に、3月17日付で地政学的な物理制約を市場判断へ接続していた記録が残っている。

底値を再現するのではない。

**価格と現実のずれを見つける手順を再現する。**

投資判断はコードではない。

それでも、

> **LLMでlintして、Gitでversioningする。**

くらいのことはできる。

自分にとっては、その方が「勘が当たった」で終わるよりずっと面白い。
